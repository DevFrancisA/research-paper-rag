# Production RAG

Question answering over your PDFs with hybrid retrieval, cross-encoder reranking, grounded answers with citations, and an evaluation suite that measures all of it.

## How it works

**Ingestion** (`POST /ingest`, the `rag/ingest_pdf` Inngest function, or the CLI)
1. Extract text page by page with pypdf, then split on sentence boundaries (512 tokens, 96 overlap). Chunks never span pages, so every citation points to an exact page.
2. Embed each chunk with OpenAI (`text-embedding-3-large`). Requests are batched (128 chunks per call) and cached by content hash, in memory and in Postgres, so re-ingesting never re-embeds the same text.
3. Compute BM25 term weights locally with fastembed.
4. Store both vectors in one Qdrant point, with `source`, `page`, `doc_id` and any custom metadata as indexed payload. Postgres records the document.

**Query** (`POST /query` or the `rag/query` Inngest function)
1. **Hybrid retrieval:** a dense vector search and a BM25 search (40 candidates each) run inside a single Qdrant query and are fused with reciprocal rank fusion. Dense search handles paraphrases, and BM25 handles exact names, codes and numbers.
2. **Metadata filtering:** filters on document, page range or custom metadata are applied inside both searches.
3. **Cross-encoder reranking:** `BAAI/bge-reranker-base` rescores the top 30 fused candidates against the question, and the best 5 are kept.
4. **Relevance threshold:** chunks scoring below `RELEVANCE_THRESHOLD` are dropped. If none remain, the system declines without calling the LLM.
5. **Source-aware prompting:** sources go in as numbered `<source id file page>` blocks. The model must cite every claim as `[n]` and must decline when the sources don't answer the question.
6. **Citation validation:** citation numbers that don't match a supplied source are removed. An answer with no valid citation becomes a refusal (`REQUIRE_CITATIONS`).
7. **Caching:** retrieval results are cached in Postgres, keyed on the question, filters, settings and a corpus version that changes on every ingest or delete. The query embedding is cached too. Each query's latency is written to `query_log` (`GET /stats`).

## Run it

### With Docker (Postgres + Qdrant + Inngest + API + UI)

```bash
cp .env.example .env        # add your OPENAI_API_KEY
docker compose up --build
```

- UI: http://localhost:8501
- API docs: http://localhost:8000/docs
- Inngest dashboard: http://localhost:8288

### Without Docker

```bash
uv sync
cp .env.example .env        # add your key, set QDRANT_URL= and leave DATABASE_URL empty
uv run uvicorn main:app --reload          # API on :8000
uv run streamlit run streamlit_app.py     # UI on :8501
```

With `QDRANT_URL` empty, Qdrant runs embedded on disk in `./qdrant_local`. With `DATABASE_URL` empty, the caches and document registry live in memory.

### Tests

```bash
uv run pytest
```

The tests run offline. They use in-memory Qdrant and the real BM25 model, with fake embeddings, reranker and LLM, so they need no API key and no Docker.

## Evaluation

Put your PDFs in a folder, then:

```bash
uv run python -m rag_production_app_test ingest data/
uv run python -m rag_production_app_test generate-benchmark      # eval/benchmark.jsonl
uv run python -m rag_production_app_test eval-all                # eval/results/*.json + REPORT.md
```

`generate-benchmark` writes 200 answerable questions, one per sampled chunk, spread across documents. Half use the document's own terms ("keyword") and half are paraphrased. The chunk each question came from is its gold answer. It also writes 50 on-topic questions that the corpus can't answer, keeping only ones a judge confirms the top retrieved chunks don't answer. Read through the file before trusting the numbers.

| Command | Measures |
|---|---|
| `eval-retrieval` | Recall@1/5/10, MRR@10, nDCG@10 and page-level hit rate for `dense` (baseline), `sparse`, `hybrid` and `hybrid_rerank`, with caching off |
| `eval-answers` | Hallucination rate and grounded-answer accuracy for the naive baseline (dense top-5, plain prompt, no threshold or citation checks) and the grounded pipeline, judged by `JUDGE_MODEL` |
| `eval-latency` | p50/p95 end-to-end latency over a workload that repeats questions, with caching off and on, plus batched vs one-at-a-time embedding time |

Definitions used in `eval-answers`:
- **Hallucinated:** the system answered, and the judge found a claim that the context it was given doesn't support.
- **Grounded-correct:** for an answerable question, the answer is supported and matches the reference. For an unanswerable question, the system declined.

The questions are generated by an LLM from your own documents, and the answers are graded by an LLM judge. Results depend on the corpus, so report them with the setup they came from (number of documents and chunks, models, number of queries). `REPORT.md` records this.

## Configuration

All settings are environment variables. `.env.example` lists the useful ones, and [config.py](src/rag_production_app_test/config.py) has the rest. `RELEVANCE_THRESHOLD` depends on the reranker model, so re-tune it with `eval-answers` if you change `RERANKER_MODEL`.
